## SCENE 3 — WHY "CONCEPT TO COMMISSIONING"?

**[ON SCREEN]**

Show an engineering-project style flow:

> Concept → Requirements → Design → Engineering → Construction → Testing → Commissioning → Operation

**[NARRATOR]**

The phrase **"concept to commissioning"** comes naturally from engineering projects.

An engineering project doesn't become a working asset simply because somebody has produced a design.

There is a journey.

You start with a concept.

You understand the requirements.

You design and engineer the system.

You build it.

You test it.

And finally, you commission it.

Commissioning is the point at which the completed system is brought into operation and we establish that it actually works as intended.

Software has a similar journey.

Replace the previous diagram with:

> Architecture

> Implementation
> ↓

**[NARRATOR]**

In software, we might describe the journey as:

Problem.

Requirements.

Domain understanding.

Architecture.

Implementation.

Testing.

Deployment.

And finally—

**working software.**

So "From Concept to Commissioning" is our way of looking at software development as an **engineering process**.

The objective isn't merely:

> "Write some code."

The objective is:

> **Take a problem and engineer a working software system.**

## SCENE 4 — WHY REAL APPLICATIONS?

**[ON SCREEN]**

Show two contrasting boxes:

**Learning in isolation**

> TypeScript
> PostgreSQL
> Next.js
> Prisma

versus

**Learning in context**

> Real problem
> → Engineering decision
> → Technology
> → Working feature

**[NARRATOR]**

So why build real applications?

Because technology becomes much easier to understand when we have a reason to use it.

Take TypeScript.

We could simply learn a list of TypeScript features.

But suppose our application receives data from a browser.

Can we trust that data?

What should happen if something is missing?

What if the value has the wrong type?

What information should our program be allowed to assume?

Now TypeScript starts to become meaningful.

Or take a database.

We could start with:

> "Today we're going to learn PostgreSQL."

But instead, suppose our application needs to record ownership of a unit over time.

An owner can change.

We need to preserve history.

We need to know who the current owner is.

We need to prevent contradictory data.

Now we have a real problem.

And that problem naturally leads us toward data modeling, relationships, constraints, queries, transactions—and eventually PostgreSQL.

**[PAUSE]**

The technology is no longer an isolated subject.

It has become a **solution to a problem**.

**[NARRATOR]**

And this leads to an important distinction about how this channel is organized.

The applications are the **laboratories**.

The subjects we study are software engineering and technology.

So the Society Management System is not the ultimate subject of this channel.

It is our first major **case study**.

Later, we may build other applications.

And those applications can become additional laboratories.

This means that when we study architecture, we can use one application as an example.

When we study TypeScript, we can use another part of the application.

When we study databases, we can return to the data problems we've already encountered.

And when we study AI-assisted development, we can use the actual development process as our example.

**TypeScript**

### E

**Next.js**

### F

**[NARRATOR]**

That's why the channel is organized into six major playlists.

### Playlist A — Real Applications

Here we'll introduce and explore the applications that become our case studies.

Our first one is the Society Management System.

### Playlist B — Architecture & SDLC

Here we'll step back and examine how software systems are engineered.

We'll use the applications as examples.

We'll look at requirements, domain modeling, specifications, architecture, testing, deployment, and the decisions that connect them.

### Playlist C — TypeScript

Here we'll learn TypeScript through real problems encountered in the applications.

We'll repeatedly use a simple pattern:

**Syntax → Context → Use Case.**

First understand the problem.

Then see the code.

Then understand why the syntax exists.

### Playlist D — PostgreSQL & Prisma

Here we'll explore relational data, PostgreSQL and Prisma through the data problems arising in the applications.

We'll move from:

**domain requirement → data model → database → application code.**

### Playlist E — Next.js

Here we'll examine how the web application is actually built.

Rather than learning framework features in isolation, we'll see them as part of real application behavior.

For example:

**Browser → HTTP → Route Handler → Authentication → Authorization → Validation → Service → Database → Response.**

### Playlist F — AI-Augmented Development

And finally, we'll explore how AI can participate in the engineering process.

But the focus won't simply be on clever prompts.

We'll ask a bigger question:

> **How should an engineer work with AI when building real software?**

## SCENE 8 — THE AI-ERA CONNECTION

**[ON SCREEN]**

Show:

> AI-assisted development

Then:

> More capable tools
> ↓
> Faster implementation
> ↓
> Greater need for engineering judgment

**[NARRATOR]**

There is another reason this approach is particularly relevant today.

AI-assisted tools are making many aspects of software implementation easier and faster.

That's good news.

But as implementation becomes more productive, the developer's role doesn't simply disappear.

The emphasis can shift.

From:

> **"How do I write this code?"**

toward:

> "What should we build?"

> "Why should we build it this way?"

> "What assumptions are we making?"

> "What could go wrong?"

> "How do we know the result is correct?"

In other words, developers increasingly benefit from understanding the **problem and the product**, not just the code.

And working on realistic applications is one way to develop that understanding.

So AI will be part of our journey—but **AI is not the identity of this channel**.

The identity is software engineering in practice.
