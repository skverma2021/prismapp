## Slide 1 — Exercise Setup

**Type:** `Exercise`

**Headline:**
> New module: Complaint Management. Here are six rules. Design the tables.

**Visual / layout:**
A card showing the scenario and rules:

**Scenario:** The society wants to track complaints from residents. A resident can file a complaint about their unit. The MC wants to assign complaints to staff, track progress, and report on resolution time. Categories and priorities are configurable by the MC.

**Rules given:**
1. C1 — A complaint belongs to exactly one unit.
2. C2 — A complaint must have a category and a priority. Both are user-managed lookups — the MC can add new categories and priorities without a code change.
3. C3 — A complaint has a lifecycle: Open → Assigned → InProgress → Resolved → Closed. Reopened is also valid. Status transitions are not hardcoded in the schema — they are enforced in service logic.
4. C4 — Notes on a complaint are append-only. A note cannot be edited or deleted after it is posted.
5. C5 — A complaint may be assigned to a staff member (an Individual). Assignment is optional and can be changed.
6. C6 — The system must know who filed the complaint and when.

**Instructions:** Pause the video. Write down: (a) how many tables you need; (b) what rule drives each table; (c) which constraints require service logic vs. a DB constraint. Resume after two minutes.

**On-screen action / demo:**
Static slide. Pause narration for two minutes.

**Key takeaway:**
Before designing, classify: C1 = FK; C2 = two user-managed lookup tables; C3 = status field (not a timeline — no temporal overlap); C4 = append-only child table; C5 = optional FK; C6 = audit FK + timestamp.

## Slide 2 — Sample Answer: The Actual CMM Schema

**Type:** `Diagram`

**Headline:**
> Four tables. All in the codebase right now. Compare your design.

**Visual / layout:**

**`ComplaintCategory`** (from C2 — user-managed lookup):
```prisma
model ComplaintCategory {
  id          Int    @id @default(autoincrement())
  description String @unique
  complaints  Complaint[]
}
```
Rule: C2 requires categories to be configurable. A separate table (not an enum) allows the MC to add new categories without a migration. Integer primary key — categories are stable master data, not random ULIDs.

**`ComplaintPriority`** (from C2 — user-managed lookup):
```prisma
model ComplaintPriority {
  id          Int    @id @default(autoincrement())
  label       String @unique
  slaHours    Int
  description String?
  complaints  Complaint[]
}
```
Rule: C2 again. Priority includes `slaHours` — even a lookup table can carry domain-relevant data. Seeded: Low (72h), Medium (48h), High (24h).

**`Complaint`** (from C1, C3, C5, C6):
```prisma
model Complaint {
  id           String    @id @default(cuid())
  ticketId     String    @unique        // MSH-{year}-{seq}, generated in service
  unitId       String
  reportedById String
  categoryId   Int
  priorityId   Int
  title        String
  description  String?
  isAnonymous  Boolean   @default(false)
  status       String    @default("Open")
  assignedToId String?                  // C5 — optional, nullable FK
  resolvedAt   DateTime?
  closedAt     DateTime?
  createdAt    DateTime  @default(now())
  updatedAt    DateTime  @updatedAt

  unit       Unit                @relation(...)
  reporter   Individual          @relation("ComplaintReporter", ...)
  category   ComplaintCategory   @relation(...)
  priority   ComplaintPriority   @relation(...)
  assignee   Individual?         @relation("ComplaintAssignee", ...)
  notes      ComplaintNote[]
}
```
Key decisions: `status` is a `String`, not an enum — allowlist enforcement is in the service (`COMPLAINT_STATUSES` constant). `assignedToId` is nullable — rule C5 says assignment is optional. `ticketId` is generated by the service (not a DB sequence) — suitable for V1 low-volume usage.

**`ComplaintNote`** (from C4 — append-only):
```prisma
model ComplaintNote {
  id          String   @id @default(cuid())
  complaintId String
  content     String
  visibility  String   // "Internal" | "Resident"
  actorUserId String   // operator identity (AppUser.id)
  actorRole   String
  createdAt   DateTime @default(now())
  complaint   Complaint @relation(...)
}
```
Rule: C4 means no `update` or `delete` operation exists in the service for notes. The schema has no `updatedAt` — there is nothing to update. `actorUserId`/`actorRole` follows the same operator audit pattern as `AuditLog` and `ContributionDetail` (AppUser identity, not an Individual FK).

**Constraint classification:**
| Rule | Enforcement |
|------|------------|
| C1 (belongs to unit) | DB FK `unitId` |
| C2 (category + priority) | DB FK `categoryId`, `priorityId` (both NOT NULL) |
| C3 (valid status) | Service: `COMPLAINT_STATUSES` allowlist check |
| C4 (notes append-only) | Service: no update/delete methods on `ComplaintNote` |
| C5 (optional assignment) | DB: nullable FK `assignedToId?` |
| C6 (who filed + when) | DB: `reportedById` FK + `createdAt` default |

**Narration:**
Here is the sample answer — and this time, you can verify it by opening `prisma/schema.prisma` right now.

Four tables: `ComplaintCategory`, `ComplaintPriority`, `Complaint`, and `ComplaintNote`. Let me explain each.

`ComplaintCategory` and `ComplaintPriority` come from rule C2. Categories and priorities are user-managed lookups. The MC can add a new category — "Maintenance", "Security", "Electrical" — without touching the code. Using a separate table instead of an enum is the right call any time the domain says "the user controls this list."

`Complaint` handles rules C1, C3, C5, and C6 together. Rule C1 is a simple FK. Rule C3 gives us a `status` string with an allowlist enforced in the service — not a DB constraint. Rule C5 gives us a nullable FK for `assignedToId`. Rule C6 gives us `reportedById` and `createdAt`.

`ComplaintNote` handles rule C4. Append-only means no `updatedAt` column — there is nothing to update. The service has no update or delete operation for notes. This is the same discipline as `ContributionDetail` — immutability is a service-layer contract, not a DB constraint.

The pattern you should notice: immutability is expressed through the *absence* of operations in the service, not through a DB constraint. The database allows any write; the service refuses to offer one.

**On-screen action / demo:**
Open `prisma/schema.prisma` and scroll to the CMM section (search for `ComplaintCategory`). Read each model aloud and point to the rule it implements.

**Key takeaway:**
A correct schema has one reason for every table and every column. Compare your design with the real schema: where did you add an extra table that was not needed? Where did you miss a column that a rule required?
A correct ERD has one reason for every table and every column. If you cannot name the rule that produced it, question whether it belongs.

## Slide 3 — Module Wrap-Up

**Type:** `Summary`

**Headline:**
> Five patterns. All derived from rules. All already in PrismApp.

**Visual / layout:**
A summary table:

| Pattern | Table in PrismApp | Rule type | Enforcement location |
|---|---|---|---|
| Timeline (FK not enough) | `UnitOwners` | Temporal | Service + transaction |
| Calendar as data | `ContributionPeriods` | Controlled vocabulary | Seed + FK |
| Append-only history | `ContributionRates` | Immutability + temporal | Service (close + insert) |
| Header + detail | `Contributions` + `ContributionDetails` | Multi-period event | Service (amount distribution) |
| System identity | `Individuals.isSystemIdentity` | Cardinality (exclusion) | Service filter |
| User-managed lookup | `ComplaintCategory`, `ComplaintPriority` | Configurable master data | Seed + CRUD + FK |
| Append-only child | `ComplaintNote` | Immutability (notes) | Service (no update/delete) |

Below: a closing line — "The CMM exercise showed two new patterns composing with patterns you already knew. The append-only note pattern is `ContributionDetail` applied to unstructured text. The user-managed lookup pattern is the same as contribution heads — just seeded differently."

**Narration:**
Let us close the module.

Five patterns — now seven, after the CMM exercise. Every one of them was derived from a domain rule, not from a preference or a framework recommendation. The timeline pattern came from the ownership overlap rule. The pre-seeded calendar came from the current-year constraint. The append-only rate history came from the financial immutability rule. The header + detail split came from the multi-period payment rule. And the CMM patterns came from rules C2 and C4.

The most important point: these patterns compose. When the CMM exercise gave you `ComplaintNote`, you had already seen the append-only principle in `ContributionDetail`. When it gave you `ComplaintCategory`, you had already seen user-managed lookups in contribution heads. The new domain did not require a new pattern — it required recognising the rule type and applying the pattern you already knew.

This is the skill this module aimed to build. Not a set of tables to memorise. A set of rule-type-to-pattern mappings that work across every domain you will ever encounter.

Open the ERD for any system you work on and ask: what rule produced this table? If nobody can answer, the design has a gap.

**On-screen action / demo:**
Show the final summary table on screen. Then briefly open `vault/01-Domain/ERD.md` and scroll through the full model — name each table and its rule type from memory. End on the mermaid diagram at the bottom of the file.

**Key takeaway:**
Domain rules do not just constrain your code — they produce your schema. Learn to read rules before you open a schema editor.
