# D-02 — The Create Pattern

---

## Slide 1 of 3 — Four Steps, No More

**Headline:** Every create handler does exactly four things. Business logic is not one of them.

**Talking points:**
- Open `app/api/blocks/route.ts` → `POST` handler. Read it as four annotated bands:

```typescript
export async function POST(request: NextRequest) {
  try {
    // Band 1 — Auth:   who is calling, and are they allowed?
    const actor = await requireMutationRole(request);

    // Band 2 — Parse:  is the input well-formed?
    const payload = await request.json();
    const input = parseCreateBlockInput(payload);

    // Band 3 — Service: do the business operation
    const data = await createBlock(input, actor);

    // Band 4 — Respond: wrap in the standard envelope
    return ok(data, 201);
  } catch (error) {
    return fail(fromUnknownError(error, getRequestId(request)));
  }
}
```

- Every exception from any band is caught by the same `catch` block. `fromUnknownError` translates it to the standard error envelope regardless of where the failure originated.
- **Why `201` and not `200`?** HTTP 201 Created means "I created a new resource." 200 OK means "I processed your request." They are both success codes, but 201 communicates intent to the client and to monitoring tools. Always use 201 for creates.
- The `actor` returned by `requireMutationRole` is `{ userId, role }`. It is passed to `createBlock` not just for auditing — it also means the service knows *who* initiated the operation. The audit log entry records this permanently.

**Visual:** The four-band annotated code block, with each band in a different color. Draw an arrow from `actor` to the `createBlock` call to highlight that identity travels through.

**Takeaway:** The route handler has four lines of logic. If you find yourself writing business rules in a route handler, move them to the service.

## Slide 2 of 3 — Inside `createBlock`: Parse → Write → Audit

**Headline:** The service is where the database and the audit trail meet.

**Talking points:**
- Open `src/modules/blocks/blocks.service.ts` → `createBlock`:

```typescript
export async function createBlock(input: CreateBlockInput, actor: AuthContext) {
  const result = await db.block.create({ data: input });

  await writeAuditLog(db, {
    actorUserId: actor.userId,
    actorRole:   actor.role,
    action:      "BLOCK_CREATED",
    entityType:  "Block",
    entityId:    result.id,
    payload:     { description: input.description },
  });

  return result;
}
```

- The function takes `input` (the typed, already-validated data shape) and `actor` (the verified identity from the JWT). It does not receive a raw `Request` object — it knows nothing about HTTP.
- `db.block.create({ data: input })` — Prisma generates an `INSERT` statement. The `id` (a UUID) and `createdAt` are generated by the database, not by application code. The returned `result` contains the database-generated values.
- `writeAuditLog` is called after the write. It records: who did it (`actorUserId`, `actorRole`), what they did (`BLOCK_CREATED`), what entity was affected (`Block`, `result.id`), and the payload snapshot.
- Note the order: write first, then audit. If the write fails, no audit entry is created — which is correct. An audit entry for a failed write would be misleading. If the audit log write fails after a successful data write, the data is still saved (the audit failure is logged separately, not surfaced to the user).
- Now look at `src/modules/blocks/blocks.schemas.ts` → `parseCreateBlockInput`:

```typescript
export function parseCreateBlockInput(payload: unknown): CreateBlockInput {
  if (typeof payload !== "object" || payload === null) {
    throw new HttpError(400, "VALIDATION_ERROR", "Payload must be an object.");
  }
  const record = payload as Record<string, unknown>;
  return {
    description: requireString(record.description, "description"),
  };
}
```

- The function accepts `unknown` — not `any`. It explicitly checks that the payload is a non-null object before casting. `requireString` validates the field is a non-empty string and throws a descriptive `HttpError` if not.

**Visual:** Data flow diagram: `request.json()` (unknown) → `parseCreateBlockInput` (throws 400 or returns `CreateBlockInput`) → `createBlock` (writes DB + audit log) → `result` (typed Block) → `ok(result, 201)`.

**Takeaway:** The parse step converts `unknown` into a typed shape. The service step converts the typed shape into a database row and an audit entry. These are separate responsibilities.

## Slide 3 of 3 — Client Side: `useCrudActions.create()`

**Headline:** The client mirrors the four-step shape in reverse.

**Talking points:**
- Open `src/hooks/use-crud-actions.ts` → `create()`:

```typescript
const create = useCallback(async <T,>(options: CreateOptions<T>) => {
  setCreateLoading(true);
  setSubmitError("");
  setSubmitSuccess("");

  try {
    const response = await fetch(options.endpoint, {
      method: "POST",
      headers: { "content-type": "application/json" },
      body: JSON.stringify(options.body),
    });

    const payload = (await response.json()) as ApiEnvelope<T>;
    if (!response.ok || !payload.ok) {
      throw new Error(toErrorMessage(payload, options.errorMessage));
    }

    options.onSuccess(payload.data);
  } catch (error) {
    setSubmitError(error instanceof Error ? error.message : options.errorMessage);
  } finally {
    setCreateLoading(false);
  }
}, [setSubmitError, setSubmitSuccess]);
```

- The function:
  1. Sets `createLoading = true` → UI shows a spinner
  2. Clears any previous error/success notices
  3. `fetch(POST, body)` → waits for the response
  4. Reads `ApiEnvelope<T>` — checks both `response.ok` (HTTP status) and `payload.ok` (business status)
  5. On success: calls `onSuccess(payload.data)` — the caller decides what to do (prepend to list, close form, show notice)
  6. On failure: calls `setSubmitError(message)` — the `NoticeStack` renders the message
  7. `finally`: always clears the loading state

- The double check `!response.ok || !payload.ok` handles two failure modes: network-level failures (the server returned 4xx/5xx) and business-level failures (the server returned 200 but `ok: false`). In practice this app always returns an error status for business failures, but both checks together are belt-and-suspenders.

**Visual:** Sequence diagram — User clicks Submit → `create()` called → fetch POST → server Route Handler (four-band) → `ApiEnvelope<T>` response → `onSuccess(data)` → row added to UI table. Show the `setCreateLoading` toggle at start and finally.

**Takeaway:** `useCrudActions.create()` handles loading state, error extraction, and success delegation. The caller provides only the endpoint, the body, and the `onSuccess` callback.
