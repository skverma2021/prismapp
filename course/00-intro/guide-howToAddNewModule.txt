\## PrismApp Learning Guide: Elementary → Intermediate



\### How to use this guide

Read each layer in order. \*\*Do not skip to the UI before understanding the backend.\*\* Each section has a "concept" paragraph, then a "read this code" list. After each section, try to explain in your own words what happens. If you can, you're ready for the next.

\### Layer 1 — Database: Schema and Prisma Setup



\*\*Concept:\*\* Everything starts with the database. Prisma defines the schema in one file, generates a TypeScript client from it, and manages migrations (SQL files that evolve the schema over time). The seed script populates initial/master data.



\*\*Read this code:\*\*



| What | File | Lines | What to notice |

|------|------|-------|----------------|

| Generator + datasource | schema.prisma | 1–7 | `provider = "postgresql"` — this single line picks the database engine |

| Simplest model | schema.prisma | 9–18 | `Block` has `@id`, `@default(uuid())`, `@unique`, `@@map("blocks")` — each decorator is a database constraint |

| Model with composite unique + index | schema.prisma | 20–35 | `Unit` has `@@unique(\[blockId, description])` (no two units with same name in a block) and `@@index(\[blockId])` for query speed |

| Relations \& onDelete | schema.prisma | 30 | `onDelete: Restrict` — Prisma won't let you delete a block that still has units |

| Migration folder | migrations | — | Each subfolder is a timestamped migration with a `migration.sql` file. Open any one to see the raw SQL Prisma generated |

| Seed script | seed.mjs | 1–40 | Uses `upsert` pattern: insert if missing, skip if exists. This makes the seed idempotent (safe to run repeatedly) |



\*\*Try this:\*\* Run `npx prisma studio` to browse the live database in a GUI. Correlate what you see with the schema file.

\### Layer 2 — Database Connection Singleton



\*\*Concept:\*\* In development, Next.js hot-reloads your code frequently. If every reload creates a new database connection, you exhaust the connection pool. The singleton pattern reuses one connection across reloads.



\*\*Read this code:\*\*



| What | File | Lines | What to notice |

|------|------|-------|----------------|

| Global declaration | db.ts | 4–6 | `declare global { var prisma }` — attaches to Node's global so it survives reloads |

| Conditional reuse | db.ts | 17–26 | In non-production: `global.prisma = db`. In production: a fresh client each time (serverless functions are ephemeral anyway) |

| Dev-only query logging | db.ts | 21 | `log: \["query", "error", "warn"]` in dev; only `\["error"]` in production |



\*\*Key takeaway:\*\* Every service file imports `{ db }` from this one file. There is never a second `new PrismaClient()` anywhere else.

\### Layer 3 — Module Structure (The Blocks Module as Template)



\*\*Concept:\*\* Each domain entity gets its own module folder under modules. A module has exactly two concerns: \*\*schemas\*\* (input parsing + validation) and \*\*service\*\* (business logic + database calls). Route handlers import from these — they never touch the database directly.



\*\*Read these three files in order:\*\*



\#### 3a. Schemas — input parsing



| What | File | Lines | What to notice |

|------|------|-------|----------------|

| TypeScript types for inputs | blocks.schemas.ts | 3–9 | `CreateBlockInput` and `UpdateBlockInput` — plain types, no Prisma dependency |

| Parse + validate | blocks.schemas.ts | 11–21 | `parseCreateBlockInput` — takes `unknown`, throws `HttpError(400)` if bad. This is the \*\*trust boundary\*\* between the internet and your code |

| At-least-one-field guard | blocks.schemas.ts | 31–33 | PATCH requires at least one field — prevents empty updates |



\#### 3b. Service — business logic + database



| What | File | Lines | What to notice |

|------|------|-------|----------------|

| Pagination with transaction | blocks.service.ts | 37–48 | `db.$transaction(\[findMany, count])` — runs both queries atomically so count matches the items |

| Case-insensitive search | blocks.service.ts | 26–32 | `contains: q, mode: "insensitive"` — Prisma's way to do `ILIKE` |

| 404 guard | blocks.service.ts | 59–63 | `getBlockById` throws `HttpError(404)` if not found — every getById in the app follows this pattern |

| Page size cap | blocks.service.ts | 13–15 | `MAX\_PAGE\_SIZE = 100` — prevents clients from requesting the entire table |

| Pagination return shape | blocks.service.ts | 50–58 | `{ items, page, pageSize, totalItems, totalPages, hasNext, hasPrev }` — every list endpoint returns this same shape |



\#### 3c. Route handlers — HTTP glue



| What | File | Lines | What to notice |

|------|------|-------|----------------|

| GET + POST on collection | route.ts | 1–28 | Each exported function name (`GET`, `POST`) is a Next.js convention — it becomes the HTTP method handler |

| Auth before logic | route.ts | 9 | `await requireReadRole(request)` — first line in every try block. Fails fast with 401/403 |

| Uniform error handling | route.ts | 13 | `return fail(fromUnknownError(error, getRequestId(request)))` — every handler uses this exact line |

| GET, PATCH, DELETE by ID | \[app/api/blocks/\[id]/route.ts](app/api/blocks/%5Bid%5D/route.ts#L1-L35) | 1–35 | `\[id]` folder = dynamic route. `params.id` comes from the URL |



\*\*Pattern to memorize:\*\* `route handler → auth guard → parse input → call service → ok(data)` or `catch → fail(fromUnknownError(error))`. Every one of the 33 routes follows this.

\### Layer 4 — API Response Envelope and Error Handling



\*\*Concept:\*\* Every API response has the same JSON shape: `{ ok: true, data }` for success, `{ ok: false, error: { code, message } }` for failure. This makes the frontend predictable — one shape to parse, always.



| What | File | Lines | What to notice |

|------|------|-------|----------------|

| Error codes | api-response.ts | 1–9 | `ApiErrorCode` union: VALIDATION\_ERROR, UNAUTHORIZED, FORBIDDEN, NOT\_FOUND, CONFLICT, etc. — stable, machine-readable codes |

| HttpError class | api-response.ts | 7–15 | Custom error: status (number) + code (string) + message. This is what services throw |

| `ok()` and `fail()` | api-response.ts | 144–156 | Two functions that build the envelope. All 33 route handlers call one of these |

| Prisma error mapping | api-response.ts | 97–135 | `P2002` (unique constraint violation) → 409 CONFLICT. This converts database errors to user-friendly HTTP responses |

| Request-ID extraction | api-response.ts | 17–19 | `getRequestId(request)` — reads the `x-request-id` header for traceability |

\### Layer 5 — Authentication and Authorization



\*\*Concept:\*\* Two separate concerns. \*\*AuthN\*\* = "who are you?" (handled by NextAuth + JWT). \*\*AuthZ\*\* = "are you allowed to do this?" (role check). The system has three roles: `SOCIETY\_ADMIN`, `MANAGER`, `READ\_ONLY`.



| What | File | Lines | What to notice |

|------|------|-------|----------------|

| Role definitions | user-role.ts | 1–33 | `MUTATION\_ROLES = \["SOCIETY\_ADMIN", "MANAGER"]`, `READ\_ACCESS\_ROLES` includes all three |

| Auth guard functions | authz.ts | 79–89 | `requireReadRole` and `requireMutationRole` — one line each, delegates to `requireRole` |

| JWT token extraction | authz.ts | 49–67 | `getAuthContext` — parses the JWT, extracts userId + role, throws 401 if missing |

| Server-side session guard | layout.tsx | 5–8 | `requireServerAppSession` — redirects unauthenticated users before any dashboard page renders |

| Proxy: request-ID injection | proxy.ts | 1–22 | Middleware that runs on every `/api/\*` request. Generates UUID, attaches to headers. This is how errors in logs can be traced back to a specific request |

\### Layer 9 — How Everything Connects (Request Lifecycle)



Trace one request end-to-end to see all layers working together:



```

1\. User clicks "Save" on a new block

2\. Browser calls POST /api/blocks with JSON body

3\. proxy.ts intercepts → generates x-request-id → attaches to headers

4\. app/api/blocks/route.ts POST handler runs:

&#x20;  a. requireMutationRole(request) — checks JWT, verifies SOCIETY\_ADMIN or MANAGER

&#x20;  b. request.json() — reads body

&#x20;  c. parseCreateBlockInput(payload) — validates input, throws 400 if bad

&#x20;  d. createBlock(input) — calls db.block.create()

&#x20;  e. ok(data, 201) — wraps in { ok: true, data }

&#x20;  f. If anything threw: fail(fromUnknownError(error, getRequestId(request)))

5\. Browser receives { ok: true, data: { id, description, ... } }

6\. useCrudActions hook updates local state, triggers refetch

```

\### How to Use This to Build Your Own Project



Once you understand the layers above, building a new project means:



1\. \*\*Design your schema\*\* in schema.prisma — models, constraints, indexes, relations

2\. \*\*Create a module\*\* for each entity under `src/modules/<name>/` — one `schemas.ts` (input types + parsing), one `service.ts` (business logic + Prisma calls)

3\. \*\*Add route handlers\*\* under `app/api/<name>/route.ts` — always: auth guard → parse → service → ok/fail

4\. \*\*Copy the shared components\*\* — DataTable, BrowseFilterBar, PaginationControls, NoticeStack

5\. \*\*Build pages\*\* under `app/(dashboard)/<name>/page.tsx` — use `useBrowseState` + `useCrudActions` hooks

6\. \*\*Add the nav item\*\* to navigation.ts



The patterns are identical for every entity. The only things that change are the field names, the validation rules, and the business logic.
