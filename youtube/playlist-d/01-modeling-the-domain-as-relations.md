## Scene 2 — The primary key pattern (1:00–2:00)

**Visual:** Open `prisma/schema.prisma`, the `Block` model, lines 9–18.

**Code shown:**
```prisma
model Block {
  id          String   @id @default(uuid())
  description String   @unique
  createdAt   DateTime @default(now())
  updatedAt   DateTime @updatedAt

  units Unit[]

  @@map("blocks")
}
```

**Narration:**
> "`id` is the primary key — a UUID, generated by the database default, not by
> application code. `description` is separately marked `@unique`, because 'Block A'
> can only mean one thing. `units Unit[]` isn't a column at all — it's the Prisma
> side of a relationship, the reverse direction of a foreign key that actually
> lives on `Unit`. And `@@map("blocks")` is the real Postgres table name — lower
> snake_case, because that's the SQL convention, even though the Prisma model name
> is `PascalCase`."

---

## Scene 3 — The foreign key, both directions (2:00–3:15)

**Visual:** Open the `Unit` model, lines 20–34.

**Code shown:**
```prisma
model Unit {
  id          String   @id @default(uuid())
  description String
  blockId     String
  sqFt        Int
  inceptionDt DateTime @default(now())
  createdAt   DateTime @default(now())
  updatedAt   DateTime @updatedAt

  block         Block                 @relation(fields: [blockId], references: [id], onDelete: Restrict)
  owners        UnitOwner[]
  residents     UnitResident[]
  contributions Contribution[]
  complaints    Complaint[]

  @@unique([blockId, description])
  @@index([blockId])
  @@map("units")
}
```

**Narration:**
> "Here's the actual foreign key: `blockId String`, plus `block Block @relation(fields:
> [blockId], references: [id], onDelete: Restrict)`. That single `@relation` line is
> doing three jobs at once — declaring which column is the foreign key, which column
> it points to, and what happens if someone tries to delete the block it points to.
> We'll spend all of next episode on that `onDelete` choice. For now, notice the
> shape: one real foreign key column, and four more `[]` relation fields —
> `owners`, `residents`, `contributions`, `complaints` — that don't exist as columns
> on `Unit` at all. They're the Prisma-side view of foreign keys that live on
> *other* tables, pointing back here."

---

## Scene 4 — One model, many named relations (3:15–4:30)

**Visual:** Open the `Individual` model, lines ~52–68, highlighting the five
relation fields with their `@relation("...")` names.

**Code shown:**
```prisma
model Individual {
  id     String @id @default(uuid())
  // ...
  genderType         GenderType        @relation(fields: [genderId], references: [id], onDelete: Restrict)
  ownedUnits         UnitOwner[]
  livedUnits         UnitResident[]
  contributions      Contribution[]    @relation("ContributionDepositedBy")
  reportedComplaints Complaint[]       @relation("ComplaintReporter")
  assignedComplaints Complaint[]       @relation("ComplaintAssignee")
  bookingRequests    Booking[]         @relation("BookingRequestor")
}
```

**Narration:**
> "`Individual` is the busiest model in the schema, and it shows why relations
> sometimes need a name. An individual can be the *depositor* on a contribution,
> the *reporter* on one complaint, and the *assignee* on another — three different
> relationships to two different tables, from the same person. Without the named
> `@relation("ContributionDepositedBy")` tags, Prisma would have no way to tell
> those apart. This is the real-world version of 'a person can play more than one
> role toward the same table' — and it's solved with a string label, not a
> workaround."
